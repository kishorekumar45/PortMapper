# PortMapper

[![CI](https://github.com/kishorekumar45/PortMapper/actions/workflows/ci.yml/badge.svg)](https://github.com/kishorekumar45/PortMapper/actions/workflows/ci.yml)

**Network Attack-Surface & Policy Drift Detection Engine.** A home-network monitor
built on nmap that doesn't just diff scan results against each other; it compares
what's actually running against a **declared policy** you write, and flags the gap:
unapproved open ports, missing required services, and devices it can't confidently
identify (including phones/laptops using MAC randomization). Findings are risk-scored
and rendered as a triage report.

## Quickstart

```bash
git clone https://github.com/kishorekumar45/PortMapper.git && cd PortMapper
pip install -e .
portmapper scan 192.168.1.0/24 --policy policy.yaml
```

For a live scan you'll also need the `nmap` binary on your `PATH`. No `nmap`, no root,
no network? Use `portmapper audit --xml <file> --policy policy.yaml` against a saved
scan instead (see [Usage](#usage)).

## Usage

### Live scan

```bash
portmapper scan 192.168.1.0/24 --policy policy.yaml
```

### Offline audit (against a saved nmap XML file)

```bash
nmap -sV -oX scan.xml 192.168.1.0/24
portmapper audit --xml scan.xml --policy policy.yaml
```

Both commands support `--format markdown` (default, human-readable) or `--format json`
(structured, for piping elsewhere, e.g. into a SIEM ingestion job).

## Policy-as-code

A policy is a YAML file declaring, per host (matched by MAC address), which ports are
allowed to be open (a whitelist) and which are required to be open. `home_policy.yaml`:

```yaml
# home_policy.yaml: declared "should be running" state, per device
hosts:
  - host: nas
    mac: "AA:BB:CC:00:11:22"
    allowed_ports:          # whitelist: anything else open here is drift
      - port: 22
        protocol: tcp
      - port: 445
        protocol: tcp
    required_ports:         # must be open, or it's a missing-service finding
      - port: 22
        protocol: tcp

  - host: router
    mac: "24:A4:3C:00:99:88"
    allowed_ports:
      - port: 22
        protocol: tcp
```

- Devices you don't manage (guests, IoT with randomized MACs) are simply left out of
  the file: an unmatched host is flagged for review (`new_host` or
  `unverified_identity`), never silently allowed and never a false "new device" alarm.

## Engineering decisions

**MAC identity, checked via the locally-administered bit, not IP tracking.**
DHCP-assigned IPs rotate; they can't be used to reliably recognize "the same device"
from one scan to the next. PortMapper identifies hosts by MAC instead, and explicitly
classifies each MAC as trustworthy (`KNOWN`, a real vendor-assigned OUI) or not
(`RANDOMIZED`), by checking the actual IEEE-defined locally-administered bit (the same
signal iOS/Android privacy MAC features rely on) rather than trusting nmap's OUI
vendor lookup, which depends on a database that can be stale or absent. See
`portmapper/nmap_parser.py`.

**Policy-drift evaluation is fully decoupled from raw scanning.** `DriftEngine` has zero
knowledge of nmap, subprocess calls, or XML; it only knows about `Host`/`PolicyRule`
objects. That's what makes `portmapper audit` (offline, no scan) and `portmapper scan`
(live) the *same* pipeline with different front ends, makes the drift/risk/report logic
testable with plain fixtures and no mocked network calls, and means the scan backend
(nmap today) could be swapped later without touching the actual security logic.

## Milestone 5 live validation & the WSL2 Layer-2 virtualization boundary

PortMapper was run as a real `portmapper scan` against a live home LAN from a WSL2
environment. Two concrete findings came out of that run:

**Every host correctly came back `UNVERIFIED_IDENTITY` (expected tool behavior, not a
bug).** WSL2's default networking mode NATs its virtual network
(`172.x.x.x/20`) behind the Windows host's real adapter. NAT provides IP-layer
routing to the physical LAN (pings and TCP connections to `192.168.1.x` hosts work
fine), but it does **not** provide Layer-2 adjacency. MAC addresses are only visible
via ARP, which only functions between hosts sharing the same broadcast domain; a
NAT-routed VM was never on that segment to begin with. nmap running inside WSL2
therefore has no MAC data to report for any LAN host, `nmap_parser.py` correctly
records `mac=None`/`MacStatus.UNKNOWN`, and `DriftEngine` correctly refuses to treat an
identity it can't verify as either "known" or "policy-matched": it reports
`UNVERIFIED_IDENTITY` instead of silently guessing. The same LAA-bit classification
logic that flags a phone's randomized MAC as untrustworthy (see
[Engineering decisions](#engineering-decisions)) generalizes cleanly to this case: no
usable MAC in, no false claim of identity out.
(Running PortMapper natively on the Windows host, or with WSL2's "mirrored" networking
mode, would restore L2 adjacency and real MAC visibility, noted here as a concrete,
tested constraint rather than a theoretical caveat.)

**The default `Scanner` timeout (300s) is too tight for a full unprivileged scan.** An
unprivileged (`sudo`-less) top-1000-port scan across several real Wi-Fi devices
exceeded the built-in timeout and correctly raised `NmapTimeoutError`, proving that
failure path
works end-to-end against a real, slow scan, not just a mocked one. A faster capture
(`-T4 --top-ports 200`) completed in ~4 minutes and parsed cleanly through
`portmapper audit`. Exposing nmap's timing/port-scope flags through the CLI (rather
than a fixed default) is the concrete follow-up this surfaced, tracked in
[Roadmap](#roadmap).

## How it works

```
Scanner / nmap_parser  →  DriftEngine  →  RiskScorer  →  Reporter
   (live or offline)      (vs. policy)   (severity)    (markdown/json)
```

## Roadmap

Milestones 1-4 (domain models, risk scoring, nmap integration, CLI) are complete, plus
an initial round of live-network validation (see above). Not yet built:
- `portmapper diff <scan1.xml> <scan2.xml>`: direct scan-to-scan comparison, no policy
  required (distinct from `audit`'s policy-vs-scan comparison).
- CLI-exposed nmap timing/port-scope options (`--top-ports`, `-T4`-equivalent), and a
  configurable `Scanner` timeout: the concrete gap live validation surfaced.
- Further false-positive tuning against a real home network over time.
- Cross-scan history (`sqlite3`) for real `first_seen`/`last_seen` tracking.
- Scheduling and alerting for recurring scans.
